# Session retrospective

Read [the retrospective template](template.md). Ground observations in the
session, the current diff and existing guidance. Propose a change only when it
would have altered the outcome, is likely to recur and is not already covered
by a check or rule.

Keep observations separate from proposed edits. Name the owning file and a
specific replacement or addition; avoid accumulating generic advice or storing
incident transcripts as instructions. Distinguish developer-session learning
from product decisions about jobs, caches, telemetry, quality gates or trust
policy.

Present the retrospective and stop. The request to run a retro alone does not
authorize applying edits, changing permissions, publishing, contacting external
systems or opening tickets. A broader explicit request to apply proposals does.
If no supported improvement remains, say "No harness changes proposed."
